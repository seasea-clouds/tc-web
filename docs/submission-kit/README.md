# 投稿工具包（Submission Kit · 博客 + 法规 · 自检脚本 v1.64）

这是 sinotradecompliance.com 的投稿工具包，**博客文章与法规文章共用同一个包、同一套检查脚本**。
你写 **48 个语言**的同一篇内容（+ 博客需要配图），用本包里的脚本自检通过后，把 zip 交回即可直接上线——我们不做二次润色，**脚本通过即定稿**。

两类内容怎么区分：`submission.json` 里**必填**的 `kind` 字段——`"blog"` 或 `"regulation"`，**必须写明，没有默认值**（不写直接报 M10 错误）。
法规的字段与正文结构与博客略有不同，见 SPEC.md 第 12 节；**其余规则一条不少，完全相同**。

> **文档分工，各司其职**：
> **SPEC.md = 全部验收规则**（目录结构 / frontmatter / 48 语言 / 正文 / 图片 / 红线 / ST 写作纪律 / P 一致性，含完整规则表）——查"规则是什么、为什么被判错"去那里；
> **本 README = 使用说明**（上手步骤、脚本命令、输出解读、流程、避坑）——不重复规则正文。
> 两份文档均为 v1.64。

## 1. 三分钟上手

```bash
# 1) 复制模板
cp -r template-blog my-article
# 2) 改 submission.json 与 content/en/<slug>.mdx，再把 48 个语言都写齐
# 3) 制图（webp），放到 my-article/images/<slug>/
# 4) 自检；通过后让脚本直接打包（0 error 才出 zip）
python3 submitter_check.py my-article
python3 submitter_check.py my-article --pack=my-article-submission.zip
```

自检输出 `结果：PASS（0 error）` 就可以提交；有 error 就按提示改，一条都不要留。
推荐用 `--pack` 一步到位：检查不通过时脚本拒绝出包，打出的 zip 一定是对应当次检查通过版本的快照。

## 2. 包里有什么（博客 + 法规两套模板）

```
README.md              本文件（使用说明）
SPEC.md                全部验收规则（含 ST/P 规则表，被判错先查这里）
locales.json           48 语言代码 / 目录名 / 语言名
glossary.json          术语表（改词形前先查这里，避免同一概念各语言写法不一致）
submitter_check.py     自检与打包脚本（纯 Python 标准库，无需安装依赖）
template-blog/         空白模板：博客用（submission.json + 一个 en 骨架）
template-regulation/   空白模板：法规用（多出 docNumber/issuer/status 等字段、正文带原文分隔标记）
sample/                两篇**完整合格**的 48 语言样例：sample/blog/ 与 sample/regulation/ 各一篇
```

**投法规**：从 `template-regulation/` 起步，正文用 `<!-- original -->` 一行把「解读」与「全文译本」隔开
（分隔线前＝我们的分析，分隔线后＝该语言的官方文本全文）。法规不使用配图。
字段含义与法规专属规则（R10–R15）见 SPEC.md 第 12 节。

`sample/` 就是最终该长什么样的唯一标准。**按类型分成两个子目录**，每个子目录可以放任意多篇：

```
sample/
├── blog/                                    博客（kind: blog，带 2 张配图与结尾 CTA）
│   └── sample-china-entry-checklist/
│       └── another-blog-slug/               ← 想放几篇放几篇
└── regulation/                              法规（kind: regulation，无配图、有 original 分隔标记）
    └── sample-import-food-producer-registration/
        └── another-regulation-slug/
```

每篇的内部结构与投稿包完全一样（`submission.json` + `content/<48 语言>/<slug>.mdx` + 可选 `images/`）。
放在 `blog/` 下的稿件其 `kind` 必须是 `"blog"`，放在 `regulation/` 下的必须是 `"regulation"` —— 放错文件夹会报 M11。

> **样例的正文是压缩过的**：法规样例的官方译本段只保留两条，真实投稿**必须交全文**
> （整部法规的每一条，不是节选）。样例只为示范结构与字段，篇幅不代表实际要求。

想看某一类怎么写，就打开对应那篇。**建议先跑一遍样例，确认你的环境正常：**

```bash
python3 submitter_check.py sample
# → 结果：PASS（0 error, 2 warning）  两个 warning 都是「英文正文偏短」，样例为控制体积故意短
```

## 3. 交付目录（必须长这样）

```
<你的包>.zip
├── blog/
│   └── <slug>/
│       ├── submission.json        ← kind 必须是 "blog"
│       ├── content/
│       │   ├── en/<slug>.mdx
│       │   ├── zh/<slug>.mdx
│       │   └── …共 48 个语言目录（缺一即拒）
│       └── images/
│           └── <slug>/
│               ├── cover.webp      ← 博客必需，精确 1200×630
│               └── fig-01.webp …   ← 正文配图，宽 ≥1200，单张 ≤400KB
└── regulation/
    └── <slug>/                     ← kind 必须是 "regulation"，images 必须是 []
        └── …（结构与博客相同）
```

一个 zip 可以放**任意多篇**：`blog/` 与 `regulation/` 下各自并列多个 `<slug>/` 即可。
**只认这两个目录**（v1.63 硬切换）：旧的 `articles/` 布局会直接退回，不再兼容。
逐字节要求见 SPEC 第 1 节。

## 4. 自检与打包：命令与输出

### 4.1 命令一览

| 命令 | 用途 |
|---|---|
| `python3 submitter_check.py <zip\|目录>` | 投稿包全量自检 |
| `… --pack[=输出.zip]` | 自检通过后由脚本打包（0 error 才出 zip） |
| `… --json` | 机器可读输出（含 `packed` 字段，可接 CI） |
| `… --quiet` | 只看结论行 |
| `… --no-parity` | 跳过跨语言一致性（P02/P03/P04/P11/P18–P29/L06），精简包或样例用 |
| `… --master=<lang>` | 指定跨语言比对的基准语言（默认中文 `zh`，其次 `en`） |
| `python3 submitter_check.py <draft.md> --body [--until=<标记>]` | 单篇草稿写作纪律自检；`--until` 截掉草稿工作附录 |

退出码：**0** = 通过（无 error）；**1** = 存在 error（需返工）；**2** = 用法错误。

### 4.2 输出怎么读

```
  [WARN ] W02 fr/green-coffee-beans-china 存在超长段落（612 字符）
------------------------------------------------------------
结果：PASS（0 error, 1 warning）→ 可提交
打包完成: my-article-submission.zip（55 文件, 842.3 KB）
```

- 每行 finding 格式：`[级别] 规则编号 文章/语言 :: 详情`。
- `error` 必须清零；`warning` 只是提醒，可以不改（但建议顺手清）。
- 被判错的规则编号去 **SPEC** 对应章节查定义与改法（速查表见下）。

## 5. 最容易踩的 8 个坑

1. **只交了 30 个语言** → 必须 48 个，清单见 `locales.json`。
2. **非英文文件里 title/excerpt 还是英文** → 每篇都要真翻译；任意两语言之间也不得完全相同（L06）。
3. **图片是 jpg/png** → 只收 webp；cover 必须 1200×630。
4. **CTA 写成 `/quote/` 或没带语言前缀** → 必须是 `[本语言的联系我们](/<lang>/packages/)`。
5. **正文把 MOA / CFDA 当作现行机构** → 现为 MARA / NMPA；写沿革时注明 `formerly`。
6. **列表项之间留空行** → 渲染会碎成多个列表。
7. **标题里用冒号或破折号作分隔** → F03 报错；词内连字符 `e-commerce` 与数字区间 `2–4` / `S0–S13` 合法，分句用逗号/句号。
8. **图片没被正文引用**（cover 除外）→ 一律判错；同一图片被引用多次同样判错（P01）。
9. **同一内容在不同语言里结构不同** → 列表在某些语言被压成散文、图在某些语言跑到列表前面、表格行数或列表条目数对不上，都会被 P21/P22/P23 判错。**写完第一批语言后，先拿中文当基准（脚本默认如此），把另外 47 个语言的块序列逐块对齐**，比事后返工省事得多。
10. **金额用了符号或 ISO 代码** → `$50` / `¥5000` / `€360` / `500 zł` / `360 USD` 都会被 P33 判错；金额一律写本土文字（「5000 元」「50 美元」）。外币**词**（euro / yen / 円）由 P32 管，符号与代码由 P33 管；符号在数字前和后都查。
11. **数字写法不同被判缺失** → 中文写「十四个」，其他语言写 “fourteen” / “quatorze” / “चौदह”，这是同义，脚本已内置数字词表归一；但若某个语言真的写了别的数值，P19 会报出来。

## 6. 本地化要求（不是机翻）

每篇非英文版本要按**目标市场**写：当地读者熟悉的品类、当地产业例子、当地出口路径。
但不得虚构「该国已获对华准入」，也不得写「该国无法向中国出口」这类绝对断言；
价格、交付周期、寄样安排、成功率承诺一律不写（脚本会拦）。
完整要求与跨语言一致性见 SPEC 第 4、8 节。

## 7. 自检通过之后

把 zip 交给对接人。站点侧会：重跑同一套脚本 → 落盘入库 → 跑站点 CI 与构建 → 部署 → 逐语言验证线上页面。
**任何一条 error 都会原样退回**，所以请务必先自己跑绿。
